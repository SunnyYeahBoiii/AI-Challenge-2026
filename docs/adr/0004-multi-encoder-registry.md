# 0004: Multi-Encoder Registry

Query-time encoding moves from one hardcoded CLIP checkpoint (ADR 0003) to a registry of three interchangeable encoders — BEiT-3, MetaCLIP, BGE-VL-large — with the constraint that only one is ever resident in memory. An admin toggles the active model through `GET`/`POST /api/admin/model`; every search-path request uses whichever encoder is currently loaded, addressed by a Milvus collection that belongs to that model alone.

**Considered alternatives:**

- **Per-request `model_id`** — let each search request pick its encoder. Rejected: with only one model loaded at a time, a request naming a different model would force a synchronous load (tens of seconds, ~4GB+ each) in the request path, and concurrent requests naming different models would race the swap lock. Model selection is an operational decision (which index is "live" right now), not a per-query one.
- **All three models loaded simultaneously** — avoids swap latency entirely. Rejected: BEiT-3, MetaCLIP and BGE-VL-large combined exceed the RAM/VRAM budget available; the whole point of this change is to support three architectures without provisioning for three at once.
- **A default model at startup** — keeps `state="ready"` from process boot instead of forcing an explicit admin action first. Rejected: with three collections that may each be indexed independently (and only BGE-VL-large's is currently backfilled — see `scripts/load_data.py`), silently defaulting to one risks serving searches against a collection nobody chose. The manager starts in `state="none"`; every encoder-dependent route returns 409 via `NoActiveModelError` until an admin loads one.
- **One shared Milvus collection across models** — keeps `load_data.py` and the search routes pointed at a single name. Rejected: the three encoders produce vectors in unrelated embedding spaces at different dimensions (1024 / 1024 / 768); mixing them in one collection would make ANN search meaningless the moment two models' vectors land in the same index. Each `Encoder` subclass declares its own `collection_name` and `embedding_dim`, and `get_milvus_client(collection_name)` caches one client per collection rather than one client total.
- **Publishing the BEiT-3 retrieval head as a vendored copy of the whole `microsoft/unilm` repo** — that repo isn't a package and pulls in training-only code (`ClipLoss`, dataset builders, DeepSpeed configs) FrameSeeker never runs. Instead, the actual transformer backbone comes from the real `torchscale` PyPI package, and only the small `BEiT3ForRetrieval` / `get_large_config` wrapper (inference-only, MIT-licensed, attributed at the top of the file) is hand-vendored into `app/services/encoders/_beit3_vendor.py`.

**Consequences:**

- `Encoder(abc.ABC)` (`app/services/encoders/base.py`) declares `load`/`unload`/`embed_text`/`embed_image`/`embed_images` plus class-level `model_id`/`collection_name`/`embedding_dim`. `ENCODER_REGISTRY: dict[str, type[Encoder]]` (`registry.py`) maps `model_id → class`; `manager.py` is the only place that ever instantiates one, guarded by a single `threading.Lock` so two concurrent admin calls can't both be mid-swap.
- `manager.swap(model_id)` always unloads whatever is active before constructing and loading the new encoder — never two sets of weights resident together. A load failure sets `state="error"` with the exception message surfaced to the admin dialog; the process does not retain the old (now-unloaded) model as a fallback, matching "no default model" — an admin must explicitly pick again.
- Every route that touches an encoder or its collection (`/api/search`, `/api/search/image`, `/api/search/video`, `/api/search/similar`, `/api/frames`, `/api/embed/text`, `/api/embed/image`) catches `NoActiveModelError` and returns HTTP 409 rather than crashing or silently returning empty results.
- `gunicorn` runs `-w 1 -k gthread --threads 4 --timeout 180 --graceful-timeout 30` instead of multiple sync workers: a second worker process would double-load whatever model is active, blowing the single-model memory budget. Threads (not processes) give concurrency for I/O-bound work (Milvus/Elasticsearch RPCs) while the swap lock serializes the one thing that must never overlap — model load/unload.
- `docker-compose.yml` mounts a persistent `hf_cache` volume at `HF_HOME` and `apps/api/weights/` (gitignored, BEiT-3's checkpoint + sentencepiece model copied in manually — not published on the Hugging Face hub) read-only into the container, so a hot-swap re-downloads nothing and a container restart doesn't re-pay a multi-GB fetch per model.
- `transformers` is pinned `>=4.40,<5` (`pyproject.toml`). Version 5's rewritten tokenizer backend no longer accepts a raw `.spm` path positionally, which broke BEiT-3's `XLMRobertaTokenizer(str(spm_path))` construction; downgrading restored the exact loading path the original `microsoft/unilm/beit3` code relies on. All three encoders were re-verified against this pinned version.
- `torchscale` (BEiT-3's backbone) pins ancient `fairscale`/`timm` on PyPI that conflict with `open-clip-torch`'s (MetaCLIP's) requirements; `[tool.uv] override-dependencies` forces the newer versions since torchscale's actual imports (`trunc_normal_`, `register_model`, `fairscale.nn.{checkpoint_wrapper,wrap}`) are stable across both.
- `to_numpy()` (`base.py`) casts to `float32` before `.cpu().numpy()` — BGE-VL-large runs in `bfloat16`, which `torch.Tensor.numpy()` cannot export directly. This is a shared helper so the fix applies to any future encoder that trades precision for memory.
- `scripts/load_data.py` now points at `BgeVlEncoder.collection_name` / `embedding_dim` as its single source of truth (the only model with a precomputed embedding index today). Backfilling MetaCLIP's and BEiT-3's collections is out of scope for this change — their collections exist in the registry and via the admin dialog they can be selected as the active *query-time* encoder, but searches against their collections return nothing until they're indexed separately.
- `apps/web`'s "Model Settings" dialog (mirroring the existing DRES settings dialog) is the only UI surface for swapping models — no per-search selector, consistent with the request-level rejection above.

**Benchmarking:** `scripts/bench_search.py --model <model_id>` now requires an explicit model and calls `manager.swap()` for warmup instead of a fixed-model warmup call; no comparative latency numbers across the three encoders have been recorded yet.

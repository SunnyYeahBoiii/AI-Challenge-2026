```markdown
# AI-Challenge-2026

AI-powered video and image search application for the AI Challenge 2026 competition. Users input text or image queries, the system finds relevant video moments using vector similarity search, and results can be submitted to the competition platform (DRES).

## Language

**Frame**:
A single extracted keyframe from a video. The atomic unit of search results.
_Avoid_: keyframe, image, shot

**Video**:
A source video containing multiple frames. Identified by `video_path` (e.g., `keyframes/K02/K02_V001`).
_Avoid_: clip, media

**Query**:
A user-provided text string or image used to search for relevant frames.
_Avoid_: search, request

**BoxQuery**:
A multi-modal search query with an id, type (text or image), content, and weight. Multiple BoxQueries can be combined for complex searches.
_Avavoid_: multi-query, search box

**Cosine Similarity**:
The relevance score between a query embedding and a frame embedding. Higher = more relevant. Used for ranking individual frames.
_Avavoid_: score, distance, similarity score

**Video Score**:
An aggregated relevance score for all frames from the same video. Used when results are grouped by video.
_Avavoid_: group score, aggregate

**DRES**:
Data Retrieval and Evaluation System — the competition platform for submitting search results. Supports KIS (Keyword In Scene), QA (Question Answering), and TRAKE (Tracking) task types.
_Avavoid_: submission system, evaluation

**Embedding**:
A 1024-dimensional vector representation of text or image content, generated by OpenCLIP DFN5B model.
_Avavoid_: vector, feature vector

**Milvus**:
Vector similarity search database. Stores frame embeddings and supports approximate nearest neighbor search.
_Avavoid_: vector database, ANN

**Elasticsearch**:
Full-text search database. Stores OCR text, ASR text, and frame metadata. Used for keyword filtering and metadata enrichment.
_Avavoid_: ES, search engine
```

- [ ] **Step 3: Create ADR-0001**

```markdown
# 0001: Turborepo Monorepo

We use Turborepo to manage a monorepo with two apps: `apps/web` (Next.js) and `apps/api` (Flask). This lets us run both dev servers with a single `pnpm dev` command, share root-level configs, and keep the frontend and backend in one repository.

**Considered alternatives:** Separate repos (no shared tooling), Nx (better Python support but heavier), bare pnpm workspaces (no task orchestration). Turborepo won for simplicity — it orchestrates JS tasks natively and handles Python via `package.json` wrapper scripts.

**Consequences:** Python setup requires a `package.json` bridge in `apps/api/` that shells out to `uv run`. Dev caching doesn't work well for Python (excluded from turbo cache). Both apps must be started together for full-stack dev.
```

```typescript
const API_BASE = "/api";

export interface SearchRequest {
  text?: string;
  topk?: number;
}

export interface Frame {
  id: string;
  frameNum: number;
  timestamp: number | null;
  frameLink: string;
  videoLink: string;
  description: string | null;
  tags: string[];
  keywords_ocr: string[];
  keywords_asr: string[];
  score: number;
  video_path: string;
}

export interface SearchResponse {
  results: Frame[];
  total: number;
}

export async function searchFrames(req: SearchRequest): Promise<SearchResponse> {
  const res = await fetch(`${API_BASE}/search`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(req),
  });
  if (!res.ok) throw new Error(`Search failed: ${res.status}`);
  return res.json();
}

export async function healthCheck(): Promise<{
  status: string;
  milvus: string;
  elasticsearch: string;
}> {
  const res = await fetch(`${API_BASE}/health`);
  return res.json();
}
```

### Next.js 16 Notes

- `cacheComponents: true` in `next.config.ts` enables ISR with App Shells (replaces experimental PPR from v15)
- `params`, `searchParams`, `cookies()`, `headers()` must be **awaited** in App Router (async Request APIs)
- `fetch` requests are **not cached by default** — use `{ cache: 'force-cache' }` to opt in
